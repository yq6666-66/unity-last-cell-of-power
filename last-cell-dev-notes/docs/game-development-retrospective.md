# 开发流程：把一次演示变成可继续开发的工程

## 目标与阶段

《最后一格电》的目标是第一人称 3D 仓库逃生游戏：维修机器人管理电量、躲避巡逻机器人并逃生。保留左上俯视小地图；桌面使用鼠标与相对朝向的 WASD，手机使用左摇杆与右侧滑动。

以下时间线按已有证据整理，不补造开发日期或完成状态。

| 阶段 | 已有成果或记录 | 不能据此宣称 |
| --- | --- | --- |
| 网页控制原型 | 公开旧单房演示及源码；交接称完成网页打开与模拟触控走看 | 真实手机通过、完整游戏完成 |
| 两房首样 | 交接称有可打开 HTML、源码和简单边界，两间相连的 12×12 米仓库 | 完整物件碰撞通过 |
| 两房精修 | 交接称完成 8 槽材质精修和独立离线美术抽核 | 精修已接入网页、实时照明通过 |
| Unity 后续开发 | 既往只读记录发现 ChapterOne 等场景与配置 | 本轮启动成功、移动或 NavMesh 问题已关闭 |
| 本次经验整理 | 梳理流程、来源、模板与独立优化规划 | 对游戏工程做了任何修改 |

重要分歧：既往 Unity ChapterOne 检查记录呈现 24×24 米单个范围，其出生点与冻结两房方案不同。两者必须分别命名、分别验收，不能把它们当成同一个版本。

## 值得保留的六条经验

### 1. 接手先做基线核对

交接文字提供线索，实际文件才决定从哪里继续。先看 README、配置、布局、核验记录、版本与入口，再检查模型完整 SHA256。文件缺失就列明所缺文件，不凭截图重建，不只比哈希前缀。

### 2. 把“大目标”拆成可验证任务

“完成游戏”无法指导一次安全改动。“复制当前首样，替换指定场景，保留操作与小地图，正常走进第二房”才有明确边界。视觉接入不同时加入 AI、充电、结局；缺规则先查原始规划，查不到再问。

### 3. 保护原件，避免版本漂移

冻结模型、已通过包、首样和角色原件只读。修改前保留备份，在新目录或独立分支做增量；记录起点提交、资产哈希和变更清单。不要为了走通路线擅自挪货架、升高视角、缩放场景或重复转换坐标轴。

### 4. 验收围绕玩家行为

测试应写“从哪里进入，输入什么，看见什么，状态如何变，失败怎样提示”。正常键盘或触控走通路线才是操作证据。脚本改坐标、瞬移、静帧和离线渲染不能替代流程验证。

### 5. 把证据类型写清楚

使用 PASS、FAIL、BLOCKED、未验证，并限定结论范围。浏览器运行不证明 Unity 运行；模拟手机不证明真机；美术通过不证明碰撞、AI 或胜负逻辑。相同视角的前后截图用于比较画面，日志和连续操作用于证明流程。

### 6. 失败有停止点

同一操作最多尝试两次；仍失败或结果不确定就记录命令、错误和下一步所需条件，不无限重试，不绕权限。每个最小单元交付后等待确认，发布、部署、合并、删除和付费单独授权。

## 建议固定下来的一轮流程

1. 核对基线：入口、版本、布局、依赖、哈希、未关闭问题。
2. 写任务单：允许变更、禁改内容、成功条件、停止点。
3. 备份并复制：保留可回退版本，不污染原件。
4. 做 1～2 个样本：只改变本轮变量。
5. 实际操作测试：固定路线、视角、尺寸和设备标签。
6. 交付：源码、依赖、启动说明、CHANGELOG、哈希、命令、日志及截图。
7. 复核并暂停：明确剩余风险，确认后再继续。
